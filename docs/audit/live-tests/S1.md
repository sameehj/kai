# S1 — Session identity (live test)

A session is created when the storage wall (Endpoint Security) sees a recognized
agent's **root exec**, inherited by descendants, and ended at **root exit**. The
project is the working directory at root exec. Unverifiable lineage (e.g. a
launchd-detached process) gets no session. A per-session record is persisted in
a registry under the control store, written only by Kai components.

## Design note (deviation from the plan's "SQLite")

The plan suggested SQLite. The audit of the existing code (walls-action-plan
rule 1: extend what exists, and say why if you rebuild) found:

- Session identity already exists (M1.2): the ES wall mints a session at an
  agent root exec, inherits it on fork/exec, writes a per-pid file under
  `<home>/sessions`, and the network wall reads it.
- All Kai actors coordinate through the `~/.kai` file tree; there is no SQLite
  anywhere, and the ES handlers must stay light (no heavy/blocking work).

So S1 adds a per-**session** registry as **one JSON file per session** under
`<home>/registry`, behind the `kai_session_*` C API. This keeps the ES handler's
write small and non-blocking (same shape as the existing per-pid write and the
grant store), stays consistent with the file-tree architecture, and is
**encapsulated** — the backend can become SQLite later without touching callers.
The registry is inside the control store, so an agent tree cannot write it. If
you still want SQLite specifically, say so and I will swap the backend behind the
same API.

## What changed

- `src/session.c` (+ `kai_session` / `kai_session_begin|record|end|get|load` in
  `kai.h`): the registry.
- `src/policy.c`: `<home>/registry` added to `kai_path_is_control_store` (an
  agent-tree writer, even a Kai-signed one, is denied).
- `StorageClient.swift`: a root exec (no inherited session) now also calls
  `kai_session_record`; root exit calls `kai_session_end`. Descendants only
  inherit (tracked by `sessionRoots`). Host app is left empty for now (deriving
  the terminal/app is a later refinement).
- CLI (read-only): `kai sessions [--json]`, `kai session show <id>`,
  `kai grants [--json] [--session <id>]`. No session or grant creation from the
  CLI. (`kai agents` is S2.)

## Automated tests — PASS (`make test`, exit 0)

`run_storage_tests` → `test_session_registry`: begin at root exec; two sessions
of one agent get distinct ids; project and audit-token pidversion recorded;
load is newest-first; end at root exit marks `ended_utc`; ending an unknown
session fails; the registry is the control store and an agent write to a record
is denied; a path-traversal id is rejected. CLI smoke-tested in a sandbox
(`kai sessions` / `session show` / `--json`).

The ES-level behaviours (inheritance by descendants, launchd-detached → no
session, spoofed env/cwd does not change the session) are properties of the ES
wall's classification, not unit-testable in the C suite; they are exercised in
the live test below. Detached-no-session rests on `kai_process_agent` returning
no agent for a launchd-parented process (already covered by the agent-identity
tests in `run_tests`).
