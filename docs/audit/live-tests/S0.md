# S0 — Stop Kai blocking itself (live test)

Fixes the Oct 25 incident where the storage wall denied Kai's own
`UserPromptSubmit` hook's read of the policy file (audit event `555e2e42ba`)
and the hook failed closed, blocking every prompt.

## Root cause (found from the audit log)

The denial record was `{"source":"storage","event":"claude (kai)",
"decision":"block","match":"kai-control-store","tool":"open",
"target":".../.kai/policy","detail":"agent open of a protected file"}`. The
`event:"claude (kai)"` and `match:"kai-control-store"` strings are produced
ONLY by the U0 control-store block in `StorageClient.authorize`, which is
guarded by `if write`. So an `O_RDONLY` read of the policy by the signed `kai`
hook was being classified as a **write**.

Cause: `openIsWrite` tested `(fflag & O_ACCMODE) != O_RDONLY`. Endpoint
Security's `open.fflag` is in the kernel **FREAD/FWRITE** convention (the access
mode is the open(2) mode + 1: `O_RDONLY -> FREAD`, `O_WRONLY -> FWRITE`,
`O_RDWR -> both`), not the `O_RDONLY/O_WRONLY/O_RDWR` convention. A read-only
open is `FREAD` (bit 0 set, FWRITE clear), so masking with `O_ACCMODE` and
comparing to `O_RDONLY` flagged **every** read as a write. The U0 write-deny
then blocked the signed kai's own policy read.

## The fix

1. **`openIsWrite` corrected**, as one source of truth in libkai:
   `kai_open_is_write(int fflag)` (`src/storage.c`) tests the `FWRITE` bit (plus
   `O_CREAT/O_TRUNC/O_APPEND`). `StorageClient.openIsWrite` now calls it. A
   read-only open is correctly a read, so the signed kai's policy read is
   exempt again, and the U0 control-store write-deny fires only on real writes.
2. **Hooks already call the signed binary.** Verified the installed Claude hooks
   invoke `/Applications/Kai.app/Contents/Resources/kai` (not a dev/unsigned
   build). No change needed; `kai_exe_path()` bakes the running binary's realpath
   in at install time, so installing from the signed app is what keeps this true.
3. **Prompt hook never blocks on Kai's own failure.** `deny_policy_error` for
   `UserPromptSubmit` now emits a non-blocking `systemMessage` warning ("Kai
   couldn't read its policy … Kai is not blocking your work") instead of
   `decision:block`. Tool-use (`PreToolUse`) still fails closed with an
   actionable `deny` message.
4. **Dev-sandbox guard.** `kai_require_sandbox_home()` aborts if `KAI_HOME` is
   unset or resolves to the real `~/.kai`; `run_storage_tests` calls it at
   startup. (`run_tests.c` could not be wired in: it holds synthetic secret
   fixtures and Kai's own hook blocks any command/editor from opening it — Kai
   protecting its fixtures. It already sandboxes via its own temp `KAI_HOME`.)

## Automated tests — PASS (`make test`, exit 0)

- `run_storage_tests` → `test_open_write_classification`: `O_RDONLY (FREAD)` is a
  READ; `O_WRONLY`, `O_RDWR`, read+trunc/append/create are writes.
- `test_s0_control_store`: policy/grants/pending are the control store; an
  ordinary file and a hook config are not; the engine denies agent read AND
  write of the policy; hook-config reads are in the read-allow set, the policy is
  not.
- `test_s0_hook_errors`: with the policy unreadable, the prompt hook does NOT
  block (emits `systemMessage`); the tool-use hook fails closed (`deny`).
- `test_s0_sandbox_guard`: a temp `KAI_HOME` is a sandbox; unset is refused.
- Full suite green: `run_tests` 106/0, storage, hooks, cli, gateway, browser,
  corpus, escape. (The cli/gateway/browser suites set up policy via `kai` and run
  inside the dev's agent tree, so `make test` builds a throwaway `kai-test` with
  the compile-only seam `KAI_TEST_DIRECT_POLICY` that skips the agent-refusal and
  pending-hold; the seam is never in the product or signed build, and the
  refusal/pending are covered by `run_storage_tests`.)

Also fixed the `make test` link error (plan item 1): `run_storage_tests` now
links the app objects (`$(CORE)` + `$(APP)` minus `main.c`) so
`kai_policy_dispatch` resolves.
